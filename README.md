# Rill

**A small, streaming API proxy written in Rust.**

Rill forwards OpenAI API requests through your own domain. Keep your existing API key and change the client's base URL. Run the same routing policy on Cloudflare Workers or as a standalone server.

English · [简体中文](README.zh-CN.md)

```text
Your client → your domain → Rill → api.openai.com
                  Cloudflare Workers / native Rust / Docker
```

## What it does

- Forwards `/v1/*`, including Responses, Chat Completions, models, files and embeddings.
- Streams request and response bodies without collecting them into memory.
- Preserves upstream status codes, error bodies, request IDs and rate-limit headers.
- Passes through your `Authorization`, `OpenAI-Project`, `OpenAI-Organization` and other API headers.
- Handles browser CORS preflight and disables response caching.
- Uses a fixed, operator-configured upstream origin. Clients cannot choose arbitrary upstream hosts.
- Requires no database, dashboard, stored provider keys or runtime model SDK.

Rill does not translate API formats or provide billing, user management or model routing. The first release supports **HTTP and SSE**, not WebSocket / Realtime transport. `/health` checks the proxy process, not OpenAI availability.

## Use your endpoint

Set your client's **Base URL** to `https://api.example.com/v1` and keep your OpenAI API key. The upstream is `https://api.openai.com`, without an extra `/api` prefix.

```bash
curl https://api.example.com/v1/models \
  -H "Authorization: Bearer $OPENAI_API_KEY"

curl -N https://api.example.com/v1/responses \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"YOUR_MODEL","input":"Say hello","stream":true}'
```

This is bring-your-own-key forwarding: the caller's OpenAI account is billed. Rill never substitutes a shared provider key. Its code does not log keys, prompts or response bodies. The proxy operator and hosting provider still handle the traffic; use an instance you trust.

## Cloudflare Workers

**Runs on Workers Free.** No database, KV, or paid add-on is required. The free plan currently includes 100,000 requests/day and 10 ms CPU/request. Waiting on upstream/network I/O does not consume CPU time; OpenAI usage is billed separately to your key. See [official limits](https://developers.cloudflare.com/workers/platform/limits/).

The simplest deployment uses the prebuilt bundle and Node.js 22+, without installing Rust:

```bash
curl -fL https://github.com/yzfly/rill/releases/download/v0.1.0/rill-worker.tar.gz | tar xz
cd rill-worker
npx wrangler@4.156.0 login
npx wrangler@4.156.0 deploy
```

Alternatively, build from source with Rust, Node.js, Wrangler and the Rust Worker build tool:

```bash
rustup target add wasm32-unknown-unknown
cargo install worker-build --version 0.8.7 --locked
npm install -g wrangler
wrangler login

cd crates/worker
wrangler dev
# Deploy when ready:
wrangler deploy
```

Wrangler invokes `worker-build --release` and uploads the generated WASM and JavaScript glue. All proxy logic is Rust; the JavaScript entrypoint is generated by Cloudflare's Rust tooling.

To use your own domain, add this to `crates/worker/wrangler.toml` after adding the domain to Cloudflare:

```toml
[[routes]]
pattern = "api.example.com"
custom_domain = true
```

You can set `workers_dev = false` when the custom domain is ready. On a separate build machine, run `worker-build --release` in `crates/worker`, copy its `build/` directory and `wrangler.prebuilt.toml`, then run `wrangler deploy --config wrangler.prebuilt.toml` from that directory. Add your domain to that configuration when using it for deployment.

Cloudflare's free plan has request and CPU quotas. A successful deployment alone does not establish OpenAI connectivity: test an authenticated request and an SSE response from your actual client network. Workers placement and upstream region restrictions can affect connectivity. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [placement](https://developers.cloudflare.com/workers/configuration/placement/).

If API clients receive Cloudflare error 1010 before reaching Rill, create a custom rule matching your API hostname and skip **Browser Integrity Check** only. This rule is available on the free plan; the rest of your zone's protections can remain enabled. See [Cloudflare's explanation](https://developers.cloudflare.com/waf/tools/browser-integrity-check/).

## Standalone Rust server

On Linux x86_64 (Debian 12 or compatible), download and run the single binary:

```bash
curl -fL https://github.com/yzfly/rill/releases/download/v0.1.0/rill-linux-x86_64.tar.gz | tar xz
./rill
```

Or build from source:

```bash
cargo build --locked --release -p rill-server
./target/release/rill
# Listening at 127.0.0.1:8787
```

Put the server behind your existing HTTPS reverse proxy. For example, with Caddy:

```caddyfile
api.example.com {
    reverse_proxy 127.0.0.1:8787 {
        flush_interval -1
    }
}
```

The server supports graceful shutdown on Ctrl+C and Unix SIGTERM. It does not retry requests or follow upstream redirects automatically.

## Footprint

Measured for 0.1.0 on Linux x86_64: **3.35 MiB** executable, approximately **3.9 MiB** idle RSS, and **4.9 MiB** peak RSS while forwarding four concurrent 8 MiB streams from a local HTTP upstream. The server uses a single-thread async runtime. TLS, concurrency and platform affect memory use; these measurements are not a capacity guarantee.

The Cloudflare upload is approximately **524 KiB**, **162 KiB** gzipped. Wrangler reported **3 ms** startup time; this is not a measurement of per-request CPU time.

## Docker and other platforms

```bash
docker compose up --build -d
curl http://127.0.0.1:8787/health
```

The Dockerfile configures a non-root user. Compose binds to loopback so an existing HTTPS reverse proxy can front it. The initial release includes Docker configuration, but the image has not been built and run in Docker. Platforms that accept a Dockerfile, such as Fly.io, Railway or Render, can use the same server image. These are deployment options, not claims of tested platform integrations. `PORT` is supported for container platforms.

| Setting | Native server | Cloudflare Worker |
| --- | --- | --- |
| `RILL_UPSTREAM` | Environment variable | Wrangler variable |
| Default upstream | `https://api.openai.com` | `https://api.openai.com` |
| `RILL_LISTEN` | Default `127.0.0.1:8787` | Not applicable |
| `PORT` | Binds `0.0.0.0:$PORT` unless `RILL_LISTEN` is set | Not applicable |

`RILL_UPSTREAM` must be an HTTP(S) **origin**, without credentials, `/v1`, query or fragment. Set it only to an upstream you trust with the caller's API key. HTTP is useful for local integration tests; use HTTPS for remote upstreams.

## Development

```bash
cargo fmt --all --check
cargo test --locked
cargo clippy --locked -p rill-core -p rill-server --all-targets -- -D warnings
cargo check --locked -p rill-worker --target wasm32-unknown-unknown
(cd crates/worker && worker-build --release)
# From the repository root, exercise the WASM bundle in the local Workers runtime:
node scripts/smoke-worker.mjs
```

The integration tests run against a local mock upstream without API keys or paid requests. They verify byte-preserving forwarding, incremental SSE delivery, authentication/preflight, error/header preservation and redirect handling.

| Crate | Responsibility |
| --- | --- |
| `rill-core` | Shared path, authentication and header policy |
| `rill-server` | Axum + Reqwest transport |
| `rill-worker` | Cloudflare Workers Rust transport |

## Scope and operations

- Anyone who can reach a deployment can use it with their own valid OpenAI key. Restrict network access or configure edge rate limits if the endpoint is private; this release does not implement per-user quotas.
- API keys stay in the client's configuration. Do not put a provider key in a public webpage or repository.
- No response cache or application request/body logs are enabled. Hosting infrastructure may have its own logging configuration.
- Cloudflare's request-size, CPU and connectivity limits still apply. The native server uses streaming bodies with a 15-second connection timeout and no fixed whole-response timeout.
